# 四节点 NVIDIA Blackwell vLLM 部署说明

本文档适用于当前四台 SR655 服务器，每台一张 NVIDIA RTX PRO 4000 Blackwell 24GB，节点间通过双口 200Gb/s ARNIC RoCE v2 网络连接。

当前环境的规范化搭建、运行和交接文档见 [四节点 Blackwell vLLM 环境搭建与运行手册](四节点%20Blackwell%20vLLM%20环境搭建与运行手册.md)。本文保留部署演进和历史测试背景；两者冲突时，以手册和 [cluster.env](cluster.env) 为准。

## 2. 模型容量结论

### Qwen3.8-27B：可以运行

推荐使用 `Qwen/Qwen3.8-27B-FP8`：

- 27B dense 模型；本次固定 commit 下载 66 个权重 shard，共 30.89GB（28.75GiB）
- 4 张卡合计物理显存约 95.6GiB
- 使用 `TP=1, PP=4`，64 层正好每节点 16 层
- 当前配置使用 FP8 KV cache、模型原生最大 262K context、每轮最多调度 4 条序列
- 默认只加载语言模型，先释放视觉编码器占用；稳定后可启用图片和视频

这里使用 pipeline parallel 而不是跨节点 tensor parallel。每台只有一张 GPU，`TP=1, PP=4` 可以避免每层进行跨节点 tensor-parallel all-reduce，是 vLLM 对一节点一 GPU 拓扑的合适布局。

### DeepSeek-V4-Flash：四张 24GB 卡不能纯 GPU 运行

以正式版 `deepseek-ai/DeepSeek-V4-Flash-0731` 为例：

- 总参数约 304B，激活参数约 13B
- checkpoint 已经是 FP4 专家 + FP8 其余参数，权重仍约 166.9GB（约 155.4GiB）
- 4 张卡只有约 95.6GiB 物理显存，按 90% 使用率仅约 86GiB 可供 vLLM 使用
- 权重至少短缺约 70GiB，还未计 KV cache、CUDA context、临时张量和 graph 空间

RDMA 只加速节点间数据传输，不会把主机内存变成 GPU 显存。NVFP4 版本也没有缩小到 96GB 以下，因为官方 checkpoint 的 MoE 专家本身已经采用 FP4。

实验上可以尝试每 GPU `--cpu-offload-gb 20` 到 `24`，但每层推理需要通过 PCIe 搬运权重，速度会很慢，且当前官方没有验证这套 4×24GB 配置。它不适合作为生产服务。合理选择是：

- 使用至少 2×96GB，推荐 4×80GB / 4×96GB 或更高配置
- 使用 DeepSeek 的蒸馏模型或更小模型
- 使用 DeepSeek 远程 API

## 4. 一次性部署

以下命令均在头节点 node0 的 `/data/vllm` 执行。三台 worker 已支持免密 SSH。

### 4.1 检查四个节点

```bash
cd /data/vllm
chmod 600 cluster.env
chmod +x scripts/vllm_cluster_*.sh

./scripts/vllm_cluster_ctl.sh sync-files
./scripts/vllm_cluster_ctl.sh preflight
```

四台机器都应显示：

```text
GPU: NVIDIA RTX PRO 4000 Blackwell, 12.0, 24467 MiB, 580.159.04
RDMA: 2 active link(s)
GPUDirect module: loaded
```

### 4.2 构建和分发镜像

```bash
# 只在头节点构建一次，并执行容器内 GPU 自检
./scripts/vllm_cluster_prepare.sh build

# 将完全相同的镜像传到三个 worker
./scripts/vllm_cluster_ctl.sh sync-image
```

`cluster.env` 固定了已核验的 vLLM nightly digest，防止四节点拉到不同版本。Qwen3.8 和 sm_120 支持变化很快，不建议随意换成旧稳定版。

### 4.3 下载和分发模型

```bash
# 下载到 /data/vllm/models/Qwen_Qwen3.8-27B-FP8
./scripts/vllm_cluster_prepare.sh download

# 离线检查 config、index 和全部 safetensors shard
./scripts/vllm_cluster_prepare.sh verify-model

# 通过私网复制到其他节点的相同绝对路径
./scripts/vllm_cluster_ctl.sh sync-model
```

每个节点必须有完整模型副本。不要让四个 Ray worker 首次启动时各自从 Hugging Face 下载，否则版本和启动时序不可控。

### 4.4 启动 Ray 和 vLLM

```bash
./scripts/vllm_cluster_ctl.sh start
./scripts/vllm_cluster_service.sh start
./scripts/vllm_cluster_service.sh logs
```

成功时 `ray status` 应稳定显示 4 个 active node 和 4 个 GPU。当前镜像只安装 vLLM 所需的 Ray cgraph 依赖，未启用可选 dashboard。

首次启动需要加载四个 pipeline stage 并编译 kernel，耗时可能较长。另开终端查看：

```bash
./scripts/vllm_cluster_service.sh status
./scripts/vllm_cluster_ctl.sh status
```

API 就绪后测试：

```bash

```

或直接调用：

## 6. 验证 RDMA / GPUDirect

启动时默认 `NCCL_DEBUG=INFO`。需要详细确认时临时改成 `NCCL_DEBUG=TRACE`，同步配置并重启，然后检查：

```bash
docker exec vllm-ray-node grep -E 'NET/IB|GDRDMA|NET/Socket' /var/log/vllm/server.log
```

判定标准：

- `NET/IB` 或 `[send] via NET/IB/GDRDMA`：使用 ARNIC/RDMA；后者明确表示 GPUDirect RDMA
- `[send] via NET/Socket`：退回普通 TCP，需要检查 provider、HCA、GID 和 peer-memory

当前 ARNIC 使用定制 userspace provider：

```text
<ARNIC_RDMA_ROOT>
```

节点脚本会把该目录只读挂入容器，并设置：

```text
NCCL_IB_HCA=arnic_0,arnic_1
NCCL_IB_GID_INDEX=1
NCCL_IB_DISABLE=0
LD_LIBRARY_PATH=<ARNIC provider>/lib
```

不要删除这个目录，也不要只挂载 `/dev/infiniband`。缺少 `libarnic-rdmav34.so` 时 NCCL 会退回 socket。

## 7. 稳定后调优

当前已验证配置：

```text
MAX_MODEL_LEN=262144
MAX_NUM_SEQS=4
MAX_NUM_BATCHED_TOKENS=2048
GPU_MEMORY_UTILIZATION=0.90
ENFORCE_EAGER=false
MAX_CUDAGRAPH_CAPTURE_SIZE=4
LANGUAGE_MODEL_ONLY=true
ENABLE_PREFIX_CACHING=true
SPECULATIVE_CONFIG=''
```

CUDA Graph 已完成 eager A/B 测试并保留。下面是较早的 `MAX_NUM_SEQS=8`、`MAX_NUM_BATCHED_TOKENS=4096`、Graph capture 8 实验，用于证明 Graph 本身有效，不代表当前调度上限：

| 模式 | 并发 | 输出吞吐 | 平均 TTFT | 平均 TPOT | 平均 E2E |
| --- | ---: | ---: | ---: | ---: | ---: |
| eager | 1 | 18.65 tok/s | 353 ms | 53.04 ms | 27.46 s |
| CUDA Graph（历史 capture 8） | 1 | **20.63 tok/s** | **318 ms** | **47.95 ms** | **24.82 s** |
| eager | 8 | 131.78 tok/s | **1.73 s** | 57.39 ms | 31.05 s |
| CUDA Graph（历史 capture 8） | 8 | **142.60 tok/s** | 1.88 s | **52.50 ms** | **28.70 s** |

该历史 A/B 中，Graph 将单并发和并发 8 的输出吞吐分别提高约 10.6% 和 8.2%。后续面向并发 1 至 4，将 capture 上限收敛为 4，并把 prefill chunk 调为 2048。当前 KV pool 为 1,208,272 tokens，262K 静态并发估算 4.61x；`262,112 输入 + 32 输出` 边界请求已再次成功。因此当前保留 `ENFORCE_EAGER=false` 和 `MAX_CUDAGRAPH_CAPTURE_SIZE=4`。

### MTP、DFlash2 和并行拓扑限制

- 不要在当前 `TP=1, PP=4` 服务设置 `SPECULATIVE_CONFIG`。Qwen3.8 checkpoint 虽有一层原生 MTP，但当前 vLLM 的 `Qwen3_5MTP` 不支持 pipeline parallel，启动会报 `NotImplementedError: Pipeline parallelism is not supported for this model.`
- DFlash2 的 Qwen3 wrapper 同样不支持 pipeline parallel，且当前实现仍有待解决的正确性改动，不能作为生产绕过方案。
- 不要只修改模型类的 `SupportsPP` 声明；上游 PP 支持 PR [vllm-project/vllm#46994](https://github.com/vllm-project/vllm/pull/46994) 包含多处调度和正确性修复，单行改接口不足以保证结果正确。
- 已尝试改为 `TP=4, PP=1` 来满足 speculative decoding，但四节点任务停在 NCCL communicator 初始化，GPU 仅占约 645 MiB，未进入模型加载。当前 ARNIC 环境继续使用已验证的 `TP=1, PP=4`。
- 只有在上游合并并发布 MTP/DFlash2 的 PP 支持，或先解决跨节点 `TP=4` 的 NCCL 初始化后，才应重新做 speculative decoding 正确性与性能 A/B。

仍可继续按一次一个变量的方式调优：

1. 当前业务并发上限为 4；用真实流量分布持续复核 `MAX_NUM_SEQS=4` 和 `MAX_NUM_BATCHED_TOKENS=2048`。
2. 按输入长度分队列，并对超长请求单独限流。
3. 默认已启用 prefix cache；若业务请求几乎没有共享前缀，可测试 `ENABLE_PREFIX_CACHING=false` 的内存和吞吐变化。
4. 需要视觉输入时设置 `LANGUAGE_MODEL_ONLY=false`，重新评估显存和并发。

当前 262K 原生 context 已完成边界测试。不要直接扩展到 1M：这需要 YaRN，而且当前 1,208,272-token KV 池无法为单条 1M 请求和输出、安全余量及并发同时提供可靠容量。

## 10. 常见故障

### Ray 只有部分 GPU

```bash
docker exec vllm-ray-node ray status
docker exec vllm-ray-node ray list nodes
```

检查四节点的 `VLLM_HOST_IP` 是否分别为 `.11/.12/.13/.14`。每个节点必须使用自己的第一条 ARNIC 地址。

### `No available node types can fulfill resource request`

通常是 Ray 和 vLLM 选了不同网卡。保持 `RAY_INTERFACE=auto`，不要统一写 `ens7`，因为 3/4 号节点实际使用 `ens8`。

### NCCL 找不到 `arnic_0`

```bash
docker exec vllm-ray-node bash -lc \
  '<ARNIC_RDMA_ROOT>/bin/ibv_devinfo -d arnic_0'
```

若失败，检查 ARNIC provider 挂载和 `libnl-3-200`、`libnl-route-3-200`。Dockerfile 已安装这两个依赖。

### NCCL 使用 Socket 而不是 RDMA

在每节点检查：

```bash
rdma link show
lsmod | grep nvidia_peermem
ibv_devinfo -v | grep -E 'hca_id|GID\['
```

应看到两个 active HCA、`nvidia_peermem`，以及 IPv4 RoCE v2 地址位于 GID 1。

### 模型 OOM

按以下顺序收紧：

1. 将 `ENFORCE_EAGER=true` 并清空 `MAX_CUDAGRAPH_CAPTURE_SIZE`，排除编译或 graph capture 问题。
2. 降低 `MAX_NUM_SEQS`。
3. 降低 `MAX_MODEL_LEN`。
4. 将 `GPU_MEMORY_UTILIZATION` 从 0.90 调到 0.88。
5. 确认使用 `Qwen3.8-27B-FP8`，不是 BF16 checkpoint。
