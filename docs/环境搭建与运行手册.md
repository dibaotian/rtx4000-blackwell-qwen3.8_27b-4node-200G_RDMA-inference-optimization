# 四节点 Blackwell vLLM 环境搭建与运行手册

本文档记录 4 台 Lenovo SR655 服务器上的实际部署方法和当前运行状态。目标读者是需要重新部署、接管运维或复现实验的工程人员。

文档基准日期：2026-08-29。

## 1. 当前结论

当前生产候选服务为：

```text
模型             Qwen/Qwen3.8-27B-FP8
API 模型名        qwen3.8-27b
API 地址          http://<NODE0_IP>:8000/v1
并行方式          TP=1, PP=4
最大 context      262,144 tokens
服务框架          vLLM 0.28.1rc1.dev43+g6f7df92a8
容器 CUDA         13.0
KV cache          FP8
调度上限          4 sequences / 2,048 prefill tokens per iteration
CUDA Graph        batch 1, 2, 4
KV pool           1,208,272 tokens（262K 静态容量估算 4.61x）
服务状态          4 个 Ray 节点 active，API ready
```

选择 `TP=1, PP=4` 的原因是每台服务器只有一张 GPU。Pipeline parallel 让每个节点负责连续的一段模型层，避免 tensor parallel 在每一层都进行跨节点 all-reduce。当前 ARNIC 环境中的 `TP=4, PP=1` 实验未能通过 NCCL communicator 初始化，因此不能作为运行配置。

DeepSeek-V4-Flash checkpoint 约 166.9GB，4 张 24GB GPU 无法纯 GPU 容纳。RDMA 只能加速通信，不能扩展显存，因此本集群不部署该模型。

## 2. 物理拓扑

| 节点 | 第一条 ARNIC / Ray IP | 第二条 ARNIC IP | Linux 网卡 | GPU |
| --- | --- | --- | --- | --- |
| node0 | `<NODE0_IP>` | `<NODE0_IP2>` | `ens7`, `enp130s0` | RTX PRO 4000 Blackwell 24GB |
| node1 | `<NODE1_IP>` | `<NODE1_IP2>` | `ens7`, `enp130s0` | RTX PRO 4000 Blackwell 24GB |
| node2 | `<NODE2_IP>` | `<NODE2_IP2>` | `ens8`, `enp162s0` | RTX PRO 4000 Blackwell 24GB |
| node3 | `<NODE3_IP>` | `<NODE3_IP2>` | `ens8`, `enp162s0` | RTX PRO 4000 Blackwell 24GB |

```text
 node0 / GPU0 ─┐
 node1 / GPU0 ─┼── ARNIC RoCE fabric 0 + fabric 1（每端口 200Gb/s）
 node2 / GPU0 ─┼── PP stage 间通过 NCCL NET/IB 通信
 node3 / GPU0 ─┘

 Ray head 和 OpenAI API 位于 node0。
 NCCL 同时使用 arnic_0 和 arnic_1，实际 PP rank 由 Ray placement group 分配。
```

共同硬件和系统条件：

- 每节点 1 张 NVIDIA RTX PRO 4000 Blackwell 24GB，compute capability 12.0（`sm_120`）。
- NVIDIA driver `580.159.04`。
- 宿主机 CUDA Toolkit 12.8，驱动可运行 CUDA 13.0 容器。
- 每节点约 124GiB RAM，`/data` 至少保留 100GB 可用空间。
- Docker 29.1.3，已配置 NVIDIA Container Runtime。
- 两个 ARNIC 端口均为 200Gb/s、MTU 4096、RoCE v2。
- RDMA HCA 名称为 `arnic_0,arnic_1`，IPv4 RoCE v2 使用 GID index 1。
- 四节点均加载 `nvidia_peermem`。


```text

MODEL_REVISION=017b9c7af6b5689d5dd426a76e0bc077eb5ca20a
```


期望结果：

- Docker runtimes 包含 `nvidia`。
- `rdma link show` 至少有两个 `ACTIVE` link。
- `ibv_devinfo` 可看到 `arnic_0`、`arnic_1` 和 GID 1。
- `nvidia_peermem` 已加载；若没有，执行 `sudo modprobe nvidia_peermem`。

头节点必须能免密 SSH 到三个 worker：

```bash
ssh <NODE1_IP> hostname
ssh <NODE2_IP> hostname
ssh <NODE3_IP> hostname
```

脚本不会通过模型传递密码；SSH 和需要 root 权限的系统操作应提前由管理员配置完成。

## 5. 当前生效配置

唯一运行事实来源是 [cluster.env](cluster.env)。截至文档基准日期，关键值如下：

```bash
VLLM_IMAGE=vllm-blackwell-ray:20260828
CLUSTER_NODES=<NODE0_IP>,<NODE1_IP>,<NODE2_IP>,<NODE3_IP>
HEAD_IP=<NODE0_IP>
RAY_INTERFACE=auto

NCCL_SOCKET_IFNAME=auto
NCCL_IB_HCA=arnic_0,arnic_1
NCCL_IB_GID_INDEX=1
NCCL_CROSS_NIC=1

MODEL_ID=/models/Qwen_Qwen3.8-27B-FP8
SERVED_MODEL_NAME=qwen3.8-27b
MAX_MODEL_LEN=262144
GPU_MEMORY_UTILIZATION=0.90

TENSOR_PARALLEL_SIZE=1
PIPELINE_PARALLEL_SIZE=4
VLLM_PP_LAYER_PARTITION=''

MAX_NUM_SEQS=4
MAX_NUM_BATCHED_TOKENS=2048
ENFORCE_EAGER=false
MAX_CUDAGRAPH_CAPTURE_SIZE=4
CUDAGRAPH_CAPTURE_SIZES=

LANGUAGE_MODEL_ONLY=true
ENABLE_PREFIX_CACHING=true
SPECULATIVE_CONFIG=''
```

这套配置针对并发 1 至 4：

- `MAX_NUM_SEQS=4` 在服务端限制同时调度的序列数。
- `MAX_NUM_BATCHED_TOKENS=2048` 控制单轮 prefill token 数。
- CUDA Graph 自动捕获 batch `1,2,4`。
- `VLLM_PP_LAYER_PARTITION` 为空，使用安全的默认 `16,16,16,16` 分层。
- `LANGUAGE_MODEL_ONLY=true` 不加载视觉编码器。
- `SPECULATIVE_CONFIG` 为空，禁用 MTP/DFlash2。

[cluster.env.example](cluster.env.example) 已同步为当前可复现基线；实际运行仍以 [cluster.env](cluster.env) 为唯一事实来源。修改模板后应复制为 `cluster.env`，复核本机路径和 IP，再由头节点统一分发。

## 6. 从零部署

以下命令都从 node0 的 `/data/vllm` 执行。

### 6.1 准备配置和脚本权限

```bash
cd /data/vllm
cp cluster.env.example cluster.env
# 按第 5 节核对并修改 cluster.env
chmod 600 cluster.env
chmod +x scripts/vllm_cluster_*.sh
```

配置中的主机路径必须在四台机器上保持一致。特别是模型目录、日志目录、vLLM cache 和 ARNIC provider 路径。

### 6.2 分发文件并执行预检

```bash
./scripts/vllm_cluster_ctl.sh sync-files
./scripts/vllm_cluster_ctl.sh preflight
```

四台服务器均应识别一张 GPU、两个 active RDMA link 和已加载的 GPUDirect 模块。预检失败时不要继续构建或启动集群。

### 6.3 构建和分发镜像

```bash
./scripts/vllm_cluster_prepare.sh build
./scripts/vllm_cluster_ctl.sh sync-image
```

镜像只在头节点构建一次，再以相同 image ID 分发到三个 worker。不要在四台机器上分别拉取 `nightly`，否则构建内容可能不一致。

核对镜像：

```bash
for ip in <NODE0_IP> <NODE1_IP> <NODE2_IP> <NODE3_IP>; do
  ssh "$ip" "docker image inspect vllm-blackwell-ray:20260828 --format '{{.Id}}'"
done
```

### 6.4 下载、校验和分发模型

```bash
./scripts/vllm_cluster_prepare.sh download
./scripts/vllm_cluster_prepare.sh verify-model
./scripts/vllm_cluster_ctl.sh sync-model
```

模型必须位于每个节点的：

```text
/data/vllm/models/Qwen_Qwen3.8-27B-FP8
```

不要让 Ray worker 在首次启动时分别联网下载模型。当前运行时设置了 `HF_HUB_OFFLINE=1` 和 `TRANSFORMERS_OFFLINE=1`，模型不完整会直接启动失败。

### 6.5 启动 Ray 集群

```bash
./scripts/vllm_cluster_ctl.sh start
./scripts/vllm_cluster_ctl.sh status
```

正确状态必须包含：

```text
Active: 4 nodes
GPU: 0.0/4.0（服务启动前）
Pending: none
Recent failures: none
```

### 6.6 启动 vLLM API

```bash
./scripts/vllm_cluster_service.sh start
./scripts/vllm_cluster_service.sh logs
```

首次启动会依次完成：

1. 创建 4-GPU Ray placement group。
2. 初始化 NCCL/RDMA communicator。
3. 每节点加载一个 PP stage。
4. profile activation 和 KV cache。
5. 执行 `torch.compile` 与 CUDA Graph capture。
6. 启动 OpenAI-compatible API。

第一次编译可能持续数分钟。只要 worker CPU/GPU 仍有活动、compile cache 仍在增长且日志没有 OOM/Traceback，就不要强制终止。

另开终端检查：

```bash
./scripts/vllm_cluster_service.sh status
./scripts/vllm_cluster_ctl.sh status
```

最终应显示：

```text
vLLM process: running
API health: ready
4.0/4.0 GPU used of 4.0 reserved in placement groups
```


### 7.2 正确性测试

```bash
curl -sS http://<NODE0_IP>:8000/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-27b",
    "prompt": "17*19=",
    "max_tokens": 8,
    "temperature": 0
  }'
```

输出正文应包含 `323`。

也可以执行项目自带测试：

```bash
./scripts/vllm_cluster_service.sh test
```

### 7.3 错误日志

```bash
docker exec vllm-ray-node bash -lc \
  "grep -E 'Traceback|ERROR|out of memory|OOM' /var/log/vllm/server.log"
```

正常情况下没有匹配结果。

### 7.4 RDMA 与 GPUDirect

```bash
docker exec vllm-ray-node bash -lc \
  "grep -E 'NET/IB|GDRDMA|NET/Socket|DMA-BUF' /var/log/vllm/server.log | tail -n 100"
```

判定：

- `NET/IB`：NCCL 使用 ARNIC verbs 路径。
- `[send] via NET/IB/GDRDMA`：数据走 GPUDirect RDMA。
- `DMA-BUF is available`：GPU 支持 DMA-BUF 路径。
- `NET/Socket`：已退回 TCP，需要检查 provider、HCA、GID 和 `nvidia_peermem`。

## 8. API 使用

### 8.1 Chat Completions

```bash
curl http://<NODE0_IP>:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-27b",
    "messages": [
      {"role": "user", "content": "用一句话说明 RDMA 的作用。"}
    ],
    "max_tokens": 128,
    "temperature": 0.7,
    "chat_template_kwargs": {"enable_thinking": false}
  }'
```

### 8.2 流式返回

在请求体增加：

```json
{
  "stream": true,
  "stream_options": {"include_usage": true}
}
```

客户端应按 Server-Sent Events 解析每一条 `data:` 消息，并在收到 `[DONE]` 后结束。

### 8.3 最大 context 约束

客户端必须满足：

```text
prompt_tokens + max_tokens <= 262144
```

接近 262K 的请求应限制为并发 1。静态 KV 容量估算不是可接受延迟下的并发能力；历史压力测试中，两路和四路满 context 会触发 preemption 和重计算，尾延迟达到分钟级。

推荐在网关按输入长度分队列：

```text
短请求     < 32K
中等请求   32K - 128K
超长请求   > 128K，单独限流
```

## 10. 当前优化状态

已经保留的优化：

- FP8 checkpoint，减少权重显存。
- FP8 KV cache，支持原生 262K context。
- CUDA Graph，明显改善 decode 吞吐和 TPOT。
- Prefix cache，适合具有共享 system prompt 的请求。
- Chunked prefill，控制长 prompt 单轮调度规模。
- 自动 async scheduling；当前 vLLM 已默认启用。
- `MAX_NUM_SEQS=4`，与当前业务并发上限一致。
- `MAX_NUM_BATCHED_TOKENS=2048`；相对 4096 基线，短请求吞吐基本不变，同时改善 c4 和长 prompt 的 TTFT。

当前配置下的固定 1,024 输入 / 512 输出测试：

| 并发 | 成功/失败 | 输出吞吐 | 平均 TTFT | 中位 TTFT | 平均 TPOT | 平均 E2E |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 4/0 | 20.62 tok/s | 318 ms | 319 ms | 47.97 ms | 24.83 s |
| 2 | 8/0 | 40.91 tok/s | 440 ms | 380 ms | 48.10 ms | 25.02 s |
| 4 | 12/0 | **76.07 tok/s** | 818 ms | 963 ms | 51.03 ms | 26.89 s |

`MAX_NUM_BATCHED_TOKENS=2048` 相对 4096 的取舍：c1/c2 输出吞吐变化小于 0.1%，c4 输出吞吐提高 0.54%、平均 TTFT 降低 21.1%；32K 冷输入 TTFT 从 4.78 秒降到 4.28 秒，但该长上下文的 TPOT 从 48.47ms 增到 51.18ms。它是面向并发 1 至 4、偏重首 token 延迟的配置，不是所有 workload 都全面更快。

当前参数也已完成 `262,112 输入 + 32 输出` 边界验证：0 失败，TTFT 76.22 秒、TPOT 57.85ms、E2E 78.01 秒，输入与输出之和正好达到 262,144。

已拒绝或暂不启用的方案：

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| MTP | 禁用 | 当前 `Qwen3_5MTP` 不支持 `PP=4` |
| DFlash2 | 禁用 | Qwen3 wrapper 不支持 PP，且仍有正确性风险 |
| `TP=4, PP=1` | 禁用 | 当前跨节点 ARNIC 环境卡在 NCCL communicator 初始化 |
| 自定义 PP `17,17,17,13` | 禁用 | 混合注意力 KV block table 与 Graph warmup 不匹配 |
| 显式 Graph batch 3 | 不保留 | c3 吞吐变化约 0.05%，属于噪声 |
| `MAX_NUM_BATCHED_TOKENS=8192` | 不保留 | 32K TTFT 恶化约 41%，KV pool 减少约 6.2% |

当前配置中的 `VLLM_PP_LAYER_PARTITION=''` 必须保持为空。对 Qwen3.8 的 48 层 linear attention 与 16 层 full attention，手工跨越其 4 层周期切分可能导致不同 PP stage 的 KV group 数量不一致。失败实验出现：

```text
expected 3 block tables, got 4
```

不要仅凭 stage 显存不均就修改分层。

- [262K context 基线](logs/cluster/benchmarks/context-262k/README.md)
- [CUDA Graph 与 speculative decoding 验证](logs/cluster/benchmarks/spec-decode/README.md)
- `logs/cluster/benchmarks/concurrency-1-4/`：并发 1 至 4 的调优原始 JSON

## 11. 常见故障与恢复

### 11.1 API 显示 not ready

先看进程和日志：

```bash
./scripts/vllm_cluster_service.sh status
docker exec vllm-ray-node bash -lc \
  'cat /run/vllm-server.pid; ps -ef | grep -E "EngineCore|RayWorkerProc"; tail -n 300 /var/log/vllm/server.log'
```

首次 compile 期间 API 端口尚未监听是正常现象。若 CPU/GPU 长时间完全空闲且日志不增长，再按错误信息处理。

### 11.2 Ray placement group 残留

强制停止 distributed engine 后可能留下占用 4 GPU 的 placement group。最可靠的恢复方法是完整重启 Ray：

```bash
./scripts/vllm_cluster_service.sh stop
./scripts/vllm_cluster_ctl.sh stop
./scripts/vllm_cluster_ctl.sh start
./scripts/vllm_cluster_service.sh start
```

### 11.3 Ray 节点不足

```bash
docker exec vllm-ray-node ray status
docker exec vllm-ray-node ray list nodes
```

确认四个节点分别使用 `.11/.12/.13/.14`。保持 `RAY_INTERFACE=auto`，不要给所有节点硬编码 `ens7`，因为 node2/4 使用 `ens8`。

### 11.4 NCCL 找不到 ARNIC

```bash
docker exec vllm-ray-node bash -lc \
  '<ARNIC_RDMA_ROOT>/bin/ibv_devinfo -d arnic_0'
```

若失败，依次检查：

1. `ARNIC_RDMA_ROOT` 是否存在并只读挂载进容器。
2. `lib/libarnic-rdmav34.so` 和 provider 配置是否存在。
3. 镜像是否包含 `libnl-3-200`、`libnl-route-3-200`。
4. `/dev/infiniband` 是否可见。
5. HCA 是否为 `arnic_0,arnic_1`，GID index 是否为 1。

### 11.5 NCCL 退回 Socket

在每个节点检查：

```bash
rdma link show
lsmod | grep nvidia_peermem
ibv_devinfo -v | grep -E 'hca_id|GID\['
```

同时确认 `NCCL_IB_DISABLE=0`、`NCCL_IB_HCA=arnic_0,arnic_1` 和自定义 provider 的 `LD_LIBRARY_PATH` 已传入 worker。

### 11.6 OOM

按以下顺序回退，每次只改一个变量：

1. 确认没有并发超长请求。
2. 降低 `MAX_NUM_BATCHED_TOKENS`。
3. 降低 `MAX_NUM_SEQS`。
4. 设置 `ENFORCE_EAGER=true` 并清空 Graph 参数，排除 capture 问题。
5. 将 `GPU_MEMORY_UTILIZATION` 从 `0.90` 降到 `0.88`。
6. 最后才降低 `MAX_MODEL_LEN`。

### 11.7 回到已验证配置

先恢复第 5 节列出的关键值，再执行完整重启。启动后必须重新完成第 7 节的 metadata、正确性、日志和 RDMA 四项验收。

## 12. 安全与生产化建议

当前 `API_KEY` 为空，只允许在隔离测试网络使用。生产环境至少需要：

- 在 `cluster.env` 配置长随机 `API_KEY`，并保持文件权限 `600`。
- 使用 Nginx 或 Envoy 提供 TLS、鉴权、请求大小限制和限流。
- 不向公网暴露 `8000` 和 Ray `6379`。
- 在网关限制并发为 4，并对超长请求单独限制为 1。
- 对 prompt token 数和 `max_tokens` 做服务前校验。
- 采集 TTFT、TPOT、E2E、请求失败率、KV 使用率和 preemption 数。
- 定期备份 `cluster.env`、镜像 digest、模型 revision 和 benchmark 报告。

Ray 控制协议没有面向公网的认证和加密能力，必须运行在可信私网。

## 13. 变更验收清单

每次升级镜像、模型或性能参数后，按以下顺序执行：

```text
[ ] 四节点 preflight 通过
[ ] 四节点镜像 ID 相同
[ ] 四节点模型 revision 和 shard 完整
[ ] Ray 4 nodes active，无 pending/failure
[ ] NCCL 使用 NET/IB，DMA-BUF 可用
[ ] /v1/models 显示正确模型和 262144 context
[ ] 17*19 正确返回 323
[ ] 日志无 Traceback、ERROR 和 OOM
[ ] 并发 1、2、4 benchmark 均零失败
[ ] 262K 边界请求仍可完成
[ ] 记录变更前后 TTFT、TPOT、吞吐和 KV pool
```

任何性能收益都必须与相同输入、输出、并发、seed 和 warmup 条件的基线比较。变化小于 3% 时按测量噪声处理，不应仅为该变化增加生产配置复杂度。
