# 服务重启指导书 — 4 节点 Qwen3.8-27B vLLM

> 更新：2026-08-30 | 当前生产配置：NVFP4 TP=4 + DFlash n=7 + 128K
> 所有命令在**头节点 node0（<NODE0_IP>）的 `/data/vllm`** 执行。

---

## 0. 先判断你属于哪种重启场景

| 场景 | 情况 | 用哪节 |
|------|------|------|
| **A. 仅重启 vLLM** | Ray 集群还在跑，只想重载模型/换配置 | §2（最常用，最快） |
| **B. 重启整个集群** | Ray 也要重启（换镜像、Ray 异常、彻底重来） | §3 |
| **C. 宿主机重启后** | 服务器断电/重启过 | §4 |

**先跑这个判断当前状态**：
```bash
cd /data/vllm
./scripts/vllm_cluster_service.sh status        # vLLM 是否 running
docker exec vllm-ray-node ray status 2>/dev/null | grep -c node_   # Ray 几个节点（应为4）
docker ps | grep vllm-ray-node                  # 容器是否在
```

---

## ⚠️ 重启前必读：ctl.sh 的已知坑（TP=4 场景）

`scripts/vllm_cluster_ctl.sh` 第 19-20 行硬校验 `CLUSTER_NODES 数量 == PIPELINE_PARALLEL_SIZE`。
当前是 **TP=4, PP=1**，节点数 4 ≠ PP 1，会报错：
```
ERROR: CLUSTER_NODES count must equal PIPELINE_PARALLEL_SIZE.
```
**这会导致 `ctl.sh start/stop/status` 全部无法使用**（场景 B/C 会踩到）。

### 一次性修复（推荐，永久解决）
把校验从 `==PP` 改成 `==TP×PP`：
```bash
cd /data/vllm
# 备份
cp scripts/vllm_cluster_ctl.sh scripts/vllm_cluster_ctl.sh.bak
# 改第20行校验逻辑
sed -i 's/((${#NODES\[@\]} == PIPELINE_PARALLEL_SIZE))/((${#NODES[@]} == TENSOR_PARALLEL_SIZE * PIPELINE_PARALLEL_SIZE))/' scripts/vllm_cluster_ctl.sh
# 同步到4节点
for ip in <NODE1_IP> <NODE2_IP> <NODE3_IP>; do scp scripts/vllm_cluster_ctl.sh $ip:/data/vllm/scripts/; done
```
改完 TP=4×PP=1=4 == 4 节点，校验通过。**做过一次后场景 B/C 才能正常用 ctl.sh。**

（若不想改脚本，场景 B/C 用 §5 的手动逐节点方式绕过。）

## 1. 确认目标配置（重启后应恢复的状态）

`cluster.env` 的关键项（重启会读它，确认无误再启）：
```
MODEL_ID=/models/Qwen3.8-27B-NVFP4
SERVED_MODEL_NAME=qwen3.8-27b
TENSOR_PARALLEL_SIZE=4
PIPELINE_PARALLEL_SIZE=1
MAX_MODEL_LEN=131072
SPECULATIVE_CONFIG='{"method":"dflash","model":"/models/DFlash2-draft","num_speculative_tokens":7}'
```
检查：`grep -E "^MODEL_ID|^TENSOR_PARALLEL|^MAX_MODEL_LEN|^SPECULATIVE" cluster.env`

## 2. 场景 A：仅重启 vLLM（最常用）

Ray 集群不动，只重启 vLLM 服务进程。**中断窗口 ~2-3 分钟**（含 torch.compile + graph capture）。

```bash
cd /data/vllm

# 1. 停 vLLM
./scripts/vllm_cluster_service.sh stop

# 2. 启 vLLM
./scripts/vllm_cluster_service.sh start

# 3. 跟启动日志（可选，Ctrl+C 退出跟踪不影响服务）
./scripts/vllm_cluster_service.sh logs
```

**等待就绪**（首次启动要编译，耐心等）：
```bash
# 轮询直到 ready（通常 90-150 秒）
for i in $(seq 1 20); do
  curl -fsS http://<NODE0_IP>:8000/health >/dev/null 2>&1 && echo "READY" && break
  echo "waiting..."; sleep 11
done
```

然后跳到 §6 验证。

## 3. 场景 B：重启整个集群（Ray + vLLM）

用于换镜像、Ray 卡死、彻底重来。**前提：已做 §顶部的 ctl.sh 修复。**

```bash
cd /data/vllm

# 1. 停 vLLM
./scripts/vllm_cluster_service.sh stop

# 2. 停整个 Ray 集群（4节点）
./scripts/vllm_cluster_ctl.sh stop

# 3. 起 Ray 集群
./scripts/vllm_cluster_ctl.sh start

# 4. 确认 Ray 4 节点 active
./scripts/vllm_cluster_ctl.sh status
# 或：docker exec vllm-ray-node ray status | grep -c node_   # 应为 4

# 5. 起 vLLM
./scripts/vllm_cluster_service.sh start
```

---

## 4. 场景 C：宿主机重启后

容器 restart policy 是 `unless-stopped`，**宿主重启后容器和 Ray 会自动起，但 vLLM 服务进程不会自动起**，需手动拉。

```bash
cd /data/vllm

# 1. 确认容器已自动起来
docker ps | grep vllm-ray-node          # 应显示 Up

# 2. 确认 Ray 4 节点（若容器刚起可能要等 Ray 组网）
docker exec vllm-ray-node ray status 2>/dev/null | grep -c node_    # 等到 4

#   若 Ray 节点不全，重启 Ray 集群（需 ctl.sh 修复）：
#   ./scripts/vllm_cluster_ctl.sh start

# 3. 起 vLLM
./scripts/vllm_cluster_service.sh start
```

## 5. 备用：手动逐节点起 Ray（不改 ctl.sh 时绕过校验）

若不想改 ctl.sh，可用 node.sh 手动逐节点操作：
```bash
cd /data/vllm
# 头节点起 Ray head
ENV_FILE=/data/vllm/cluster.env ./scripts/vllm_cluster_node.sh start head
# 每个 worker 起 Ray worker（在头节点通过 ssh）
for ip in <NODE1_IP> <NODE2_IP> <NODE3_IP>; do
  ssh $ip "cd /data/vllm && ENV_FILE=/data/vllm/cluster.env ./scripts/vllm_cluster_node.sh start worker"
done
# 确认
docker exec vllm-ray-node ray status | grep -c node_    # 应为 4
# 起 vLLM
./scripts/vllm_cluster_service.sh start
```

## 6. 启动后验证（必做，逐项确认）

```bash
cd /data/vllm

# 1. 健康
curl -s http://<NODE0_IP>:8000/health && echo " ← health OK"

# 2. 模型 & 上下文长度
curl -s http://<NODE0_IP>:8000/v1/models | python3 -c "import json,sys; d=json.load(sys.stdin); print('模型:', d['data'][0]['id'], '| max_len:', d['data'][0]['max_model_len'])"
#   应显示: qwen3.8-27b | max_len: 131072

# 3. 正确性
curl -s http://<NODE0_IP>:8000/v1/completions -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-27b","prompt":"17*19=","max_tokens":8,"temperature":0}' \
  | python3 -c "import json,sys; print('17*19 =>', json.load(sys.stdin)['choices'][0]['text'])"
#   应输出: 323

# 4. Ray 4 节点无故障
docker exec vllm-ray-node ray status | grep -E "node_|failure"

# 5. 日志无错误
docker exec vllm-ray-node bash -lc "grep -cE 'ERROR|Traceback|out of memory' /var/log/vllm/server.log"
#   应为 0（或仅历史的 ActorHandle 清理噪声）
```

**全绿 = 重启成功。**

## 7. 常见故障与处理

### 7.1 启动卡住不 ready（超过 5 分钟）
首次启动要 torch.compile（~40s）+ graph capture。只要 GPU 有活动、日志在增长、无 Traceback，就继续等。
```bash
docker exec vllm-ray-node bash -lc "tail -30 /var/log/vllm/server.log"
# 看是否在 'Capturing CUDA graphs' 或 'torch.compile'——正常
```

### 7.2 报 ActorHandleNotFoundError
这是 **Ray placement group 残留**（上个 job 的 actor 跨 session 失效），常见于反复 stop/start。是 **shutdown 清理噪声，不是真失败**。
```bash
# 确认 GPU 已释放
docker exec vllm-ray-node ray status | grep GPU    # 应 0.0/4.0 used
# GPU 空了直接重试 start 即可
./scripts/vllm_cluster_service.sh start
```
若反复失败，完整重启 Ray（场景 B）。

### 7.3 KV cache 不足报错（ValueError: ... KV cache memory）
某些配置（如 TP=2）在 262K 下 KV 装不下。当前 TP=4 + 128K 不会遇到。若换配置遇到，降 `MAX_MODEL_LEN` 或调 `GPU_MEMORY_UTILIZATION`。

### 7.4 Ray 节点不全（少于4）
```bash
docker exec vllm-ray-node ray status
# 检查各节点用自己的第一条 ARNIC 地址（.11/.12/.13/.14）
# 保持 RAY_INTERFACE=auto，不要硬编码网卡名（3/4号节点用 ens8）
```
处理：完整重启 Ray（场景 B）或手动逐节点（§5）。

### 7.5 模型加载失败（找不到文件）
生产模型在 `/data/vllm/models/Qwen3.8-27B-NVFP4`（容器内 `/models/...`），4 节点都要有。
```bash
for ip in <NODE0_IP> <NODE1_IP> <NODE2_IP> <NODE3_IP>; do
  echo -n "$ip: "; ssh $ip "du -sh /data/vllm/models/Qwen3.8-27B-NVFP4 2>/dev/null | cut -f1"
done
# 应都是 22G。缺失则从头节点 rsync 补齐。
```
