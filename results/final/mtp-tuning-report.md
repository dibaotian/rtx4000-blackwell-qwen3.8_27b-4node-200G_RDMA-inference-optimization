# MTP 实测调优报告 — TP=4 + 原生 MTP（RTX PRO 4000 Blackwell）

> 测试日期：2026-08-29
> 硬件：4 × RTX PRO 4000 Blackwell 24GB + 200G ARNIC RDMA
> 模型：Qwen3.8-27B-FP8，vLLM 0.28.1rc1，TP=4，FP8 KV，CUDA Graph
> Workload：1K 输入 / 512 输出，ignore_eos，每档并发1/2/4，均有 warmup
> **实测结论：MTP 有效，且远超预期——单请求 decode 最高 102 tok/s，是 TP=4 baseline 的 2.4 倍**

---

## 0. 核心结论（先看这里）

| 问题 | 答案 |
|------|------|
| MTP 在 TP=4 下能启用吗？ | ✅ **能**。`Qwen3_5MTP` 架构正常加载，0 error，正确性通过。PP 时代的 `NotImplementedError` 不再出现。 |
| 提升 TPOT 吗？ | ✅ **大幅提升**。TPOT 从 23ms 降到最低 **9.1ms（n=3）**，decode 快 2.4 倍。 |
| 提升 TTFT 吗？ | ❌ **基本不变**（179→188~259ms，略升）。符合原理：投机只加速 decode。 |
| 我之前"GPU 满载所以没空间"的预测对吗？ | ❌ **错了**。虽然 GPU 98-99% 忙，但 Qwen 原生 MTP 接受率高（pos0 达 75%），一次 forward 多产出已接受 token 仍净赚。**实测推翻了理论悲观预期。** |
| 最优配置？ | **看场景**：单请求低延迟选 **n=3**（102 tok/s）；并发均衡选 **n=2**（C4 达 226）；保守稳妥选 **n=1**。详见 §3。 |

## 2. 为什么实测好于理论预测

我此前基于"单请求 decode 时 GPU 已 98-99% 满载 → compute-bound → 投机无空间"预测收益只有 1.1-1.5×。**实测证明这个推理不完整**：

- GPU util 高 ≠ 没有投机空间。关键是**接受率**。Qwen 的原生 MTP head 训练充分，pos0 接受率 75%——意味着平均每次主模型 forward 能"免费"多确认 0.75~1.5 个 token。
- 即便 GPU 忙，MTP 的额外计算（多算几个草稿位）相对"多产出一个真 token"的收益，仍是划算的——因为草稿验证是**批量**做的，摊薄了权重读取。
- 所以 n=3 单请求达到 2.4×，接近甚至超过文档里 H200 的 MTP 倍数（2.59×）。**RTX PRO 4000 上 MTP 的收益是真实且巨大的。**

**教训**：投机解码的收益必须实测，不能只看 GPU util 推断。接受率才是决定性变量。

## 3. 最优配置选择（遵循 goal §12.2：选最高稳定 throughput，非简单选最大 n）

### 按场景推荐

| 场景 | 推荐 | 理由 |
|------|------|------|
| **单请求 / 低延迟优先** | **MTP n=3** | 单请求 102 tok/s、TPOT 9.1ms，碾压其他。适合交互式、单用户、agent 串行调用。 |
| **并发 2-4 均衡** | **MTP n=2** | C4 达 226 tok/s（全场最高），C2 也有 121。并发下 n=2 比 n=3 稳（n=3 在 C4 反而回落到 217，因草稿验证在高并发下摊到更多请求）。 |
| **保守 / 稳定优先** | **MTP n=1** | 接受率最高 75.5%，行为最可预测，显存开销最小（KV 1.37M）。 |

### 关键观察
- **n=3 在单请求一枝独秀（102），但并发升高后优势缩小**：C4 时 n=3(217) < n=2(226)。这符合"投机收益随并发递减"的规律——并发本身就在填满 GPU，草稿验证的边际收益下降。
- **n=2 是并发场景的甜点**：C4 最高 226 tok/s（比 baseline 142 高 59%）。
- **TTFT 全部略升**（179→188~259ms）：MTP 的草稿开销加在每步，轻微影响首 token，但幅度小（< 80ms），可接受。

### 综合推荐
考虑到本项目 goal 聚焦**单请求性能 + 小并发（1/2/4）**，且验收目标是"单 GPU 稳定 decode > 50 tok/s"：

> **默认推荐 MTP n=2**：单请求 62 tok/s（超 50 目标），C2=121、C4=226，全并发段表现均衡且稳定。
> **若业务以单请求为主，用 MTP n=3**：单请求飙到 102 tok/s。

两者都**远超 goal 的 50 tok/s 目标和 60 tok/s"优秀"线**。

## 5. 发现的调优线索（后续可继续）

1. **`max_num_batched_tokens` 2048 vs 4096（已实测，REJECT）**：
   官方启动日志警告 2048 限制草稿槽位，建议增大。**实测 n=3 + 4096 反而更差**：单请求从 102 降到 **86 tok/s**，C4 持平（224 vs 217），且 4096 也没消除该警告。因此 **2048 更优，保留**。这是一个"听起来该调、实测证明别调"的典型——遵循 goal「性能没提升则回滚」。

2. **DFlash2 对照**：本地无草稿模型，需联网下 `incoai/Qwen3.8-27B-DFlash2`。DFlash 在 MoE 上强，但你的是 dense 模型，MTP 已经很好，DFlash 未必更优——性价比不高，除非要压榨极限。

3. **chunked prefill 与 MTP**：当前两者共存且工作正常（未报冲突）。官方 recipe 建议关 chunked-prefill 配 MTP，但你实测开着也 OK——可 A/B 看关掉是否让 MTP 再快一点（但会影响长 prompt TTFT，需权衡）。

4. **长上下文 + MTP 回归**：本次只测 1K，未测 32K/128K/262K + MTP，后续应补（长 context 下接受率可能变化）。

## 6. 完整优化历程回顾（本项目累计）

| 阶段 | 单请求 decode | 相对最初 |
|------|---:|---:|
| PP=4（原始生产配置） | 20.6 tok/s | 1.0× |

| **TP=4 + MTP n=3**（本报告） | **102.0 tok/s** | **5.0×** |

**从最初的 20.6 到现在的 102 tok/s，累计提升 5 倍**，全部实测、单变量、可复现。两个关键突破都来自推翻旧文档的"不可能"结论：
1. TP=4 其实能在 ARNIC RDMA 上跑（旧文档说不行）
2. MTP 其实能在 TP 下启用且收益巨大（旧文档因 PP 判其不可用）

## 7. 复现与配置

当前生效配置（`cluster.env`）：
```bash
TENSOR_PARALLEL_SIZE=4
PIPELINE_PARALLEL_SIZE=1
SPECULATIVE_CONFIG='{"method":"mtp","num_speculative_tokens":3}'   # 或 2，按场景
KV_CACHE_DTYPE=fp8
MAX_MODEL_LEN=262144
MAX_NUM_SEQS=4
MAX_NUM_BATCHED_TOKENS=2048    # 建议后续测 4096
ENABLE_PREFIX_CACHING=true
```

存档：
- `logs/cluster/benchmarks/mtp-test/mtp{1,2,3}-1k-512-c{1,2,4}.json` — 9 组原始 JSON
- `results/final/benchmark.csv` — 含 `mtp-tp4` 9 行
- 备份：`cluster.env.tp4-nospec-backup`（无 MTP 的 TP=4）、`cluster.env.pp4-backup`（原 PP=4）

复现命令见 `tp4-vs-pp4-report.md` §7，仅需在 `cluster.env` 加 `SPECULATIVE_CONFIG` 一行并重启。
