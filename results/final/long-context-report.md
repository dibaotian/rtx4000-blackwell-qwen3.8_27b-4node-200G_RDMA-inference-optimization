# 长文本输入输出能力测试报告

> 日期：2026-08-29 | 配置：NVFP4 (unsloth) + TP=4 + DFlash n=7 + FP8 KV + max_model_len 262144
> 硬件：4 × RTX PRO 4000 Blackwell + 200G ARNIC RDMA
> 测试三维度：长输入(prefill) / 长输出(generation) / 长上下文正确性(大海捞针)

---

## 0. 核心结论

| 维度 | 结论 |
|------|------|
| **长输入 prefill** | ✅ 32K/128K/262K 全部成功，TTFT 5.5s/33s/97s，prefill 5900→2700 tok/s |
| **长输出生成** | ✅ 持续生成 2K/4K tokens 稳定，**长输出比短输出更快**（198 tok/s @4K） |
| **长上下文检索** | ✅ **大海捞针全部命中**，从 1K 到 **204K tokens**，任意深度（5%/50%/95%）都能准确检索 |
| **能力退化** | ❌ 无。NVFP4 量化在超长上下文下仍准确检索，未见"长文本失忆" |

**一句话：长文本能力完整可用，可靠支持到 200K+ token 的检索，长输出高效。**

## 1. 长输入 Prefill 性能（单请求，随机数据，32输出）

> ⚠️ **已修正（见 hardware-tuning-report.md §3）**：下表初测值是**冷启动首次请求**（含 JIT/kernel 编译），严重偏大。**稳态（warmup 后）值才是真实性能**，快 8-22 倍。

| 输入长度 | 稳态 TTFT（正确）| 冷启动 TTFT（失真，勿用）| 状态 |
|---:|---:|---:|:---:|
| 32,768 (32K) | **~650 ms** | ~~5549 ms~~ | ✅ |
| 131,072 (128K) | **~1,468 ms** | ~~33039 ms~~ | ✅ |
| 262,112 (262K) | **~63,051 ms** | ~~97148 ms~~ | ✅ 边界成功 |

**解读（基于稳态值）**：
- 三档全部成功处理，无 OOM / 截断。
- **真实 prefill 很快**：32K 首字节仅 0.65s，128K 仅 1.5s——体验良好。
- **262K 边界需 63s**：超长 prefill 本身 compute 密集（attention 随长度平方增长），这个量级合理，是超长输入的固有代价。
- **教训**：benchmark 必须测 warmup 后的稳态，冷启动首次含编译开销，不可作为性能数据。

**生产建议**：<128K 输入首字节 1-2s 内，体验好；接近 262K 的请求需 ~63s prefill，应用层限并发 1 并做用户预期管理。有共享前缀的场景开 prefix cache 可让 TTFT 降到毫秒级。

## 2. 长输出生成性能（短输入1K，temp=0，DFlash）

| 输出长度 | 输出吞吐 | TPOT | 状态 |
|---:|---:|---:|:---:|
| 512（对照） | ~86-96 | ~10ms | ✅ |
| 2,048 (2K) | 188.6 tok/s | 5.2ms | ✅ |
| 4,096 (4K) | **198.2 tok/s** | **5.0ms** | ✅ |

**解读**：
- **长输出比短输出更快**（198 vs ~90 tok/s）！原因：输出越长，DFlash 投机的草稿验证越充分流水线化，warmup 开销被摊薄，稳态 decode 效率极高。
- TPOT 低至 5ms（每秒 200 token），持续生成 4K tokens 无衰减、无卡顿。
- 长输出场景（写长文档、长代码、长报告）是本配置的强项。

## 3. 长上下文检索正确性（大海捞针 Needle-in-Haystack）

**方法**：在长填充文本的指定深度埋入一个特定信息（如"密码是八六三一"），然后提问，看模型能否从长上下文中准确检索。这是验证"真正利用长上下文"而非"只是能跑"的关键测试。

| 上下文长度 | 针深度 5-10% | 针深度 50% | 针深度 90-95% |
|---:|:---:|:---:|:---:|
| ~1K | — | ✅ | — |
| ~4K | — | ✅ | — |
| ~9K | ✅ | ✅ | ✅ |
| ~20K (64K段) | ✅ | ✅ | ✅ |
| **~90K** | ✅ | ✅ | ✅ |
| **~205K** | — | ✅ | ✅ |

**全部命中，无一失误。**

**解读**：
- 从 1K 到 **204,843 tokens**，模型都能准确检索埋藏的信息。
- **针的位置（开头/中间/结尾）不影响检索**——没有"迷失在中间"（lost-in-the-middle）问题。
- **NVFP4 量化在超长上下文下未见能力退化**——这是你最担心的点，实测证明 4-bit 量化没有损害长上下文的检索能力。
- 205K token 深度 95% 命中，证明本配置的长上下文能力是**真实可用**的，不是纸面参数。

## 4. 综合评估

| 能力 | 评级 | 说明 |
|------|:---:|------|
| 超长输入处理 | ✅ 优秀 | 262K 边界成功，代价是 TTFT 长（97s@262K） |
| 长输出生成 | ✅ 优秀 | 4K 输出 198 tok/s，比短输出更快 |
| 长上下文检索 | ✅ 优秀 | 204K 任意深度全命中，无退化 |
| 量化对长文本的影响 | ✅ 无损 | NVFP4 长上下文检索与预期一致 |

### 使用建议
- **长输出场景**（长文档/代码/报告生成）：本配置强项，放心用，temp=0 时近 200 tok/s。
- **长输入场景**（长文档问答/RAG/代码库分析）：检索准确可靠，但注意 TTFT：
  - <32K：TTFT ~5s，体验好
  - 32K-128K：TTFT 5-33s，可接受
  - >128K：TTFT 数十秒到 97s，需用户预期管理，应用层限并发 1
- **超长请求排队**：接近 262K 的请求会长时间占用，建议按输入长度分队列限流（<32K / 32K-128K / >128K）。

## 5. 数据与复现

- CSV：`results/final/benchmark.csv`（`longtext` 5 行）
- 长输入/输出：`vllm bench serve --random-input-len N --random-output-len M`
- 大海捞针：Python 脚本构造 filler+needle，调 chat API，temp=0 检查检索。

```bash
# 长输入 prefill
vllm bench serve --model <nvfp4> --dataset-name random \
  --random-input-len 262112 --random-output-len 32 --num-prompts 1 --max-concurrency 1

# 长输出
vllm bench serve --model <nvfp4> --dataset-name random \
  --random-input-len 1024 --random-output-len 4096 --num-prompts 2 --max-concurrency 1 --temperature 0
```

**注**：prefill/decode 速度测试用随机数据有效（与内容无关）；大海捞针必须用真实语义文本（检索依赖语言理解）。
