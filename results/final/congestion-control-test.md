# 拥塞控制（CC）开关测试报告

> 日期：2026-08-30 | 硬件：4× RTX PRO 4000 Blackwell + 双 200G ARNIC RoCE v2
> CC 算法：CORNV2（ARNIC 自带）| 测试负载：推理高并发 c16 压测
> 操作：重载 arnic 驱动 `disable_cc=0` 打开 CC + 配置交换机（用户完成）

---

> ⚠️ **重要更新（多档测试修正）**：本报告仅测了 c16 单档，得出"CC 一律有代价"。
> 后续多档测试（`cc-detailed-comparison.md`）发现 **CC 效果强依赖并发**：
> 低并发（c1）CC 有代价（P99 +49%），高并发（c16）CC 反而更好（吞吐 +3.1%）。
> **结论以 `cc-detailed-comparison.md` 为准**：低并发关 CC，高并发开 CC。

## 0. 核心结论

**打开拥塞控制（CC）显著改善网络质量（丢包 −79%、重传 −32%），但推理性能略降（吞吐 −2.5%、P99 延迟 +13%）。**

这是拥塞控制的典型权衡：CC 通过主动限速避免丢包/重传，代价是峰值吞吐略降。**是否值得开，取决于你更在意"网络稳定性"还是"极限吞吐"。**

---

## 1. 测试方法

- **单变量**：仅切换 `disable_cc`（Y→N），其余配置（NVFP4 + TP=4 + DFlash n=7）不变。
- **相同负载**：c16 高并发压测（1024 输入），拥塞计数器采 30s 窗口；性能测 48 请求 1024/256。
- **CC=ON 性能测 2 次**确认非噪声。
- CC 状态确认：`disable_cc=N`, `cc_state=1`, `cc_algorithm=CORNV2`（4 节点一致）。

---

## 2. 网络质量对比（30s 窗口，相同 c16 负载）

| 指标 | CC=OFF | CC=ON | 变化 |
|------|---:|---:|---:|
| **retx（重传）** | 481 | 326 | **−32%** ✓ |
| **drop（丢包）** | 705 | 150 | **−79%** ✓✓ |
| ecn（拥塞标记） | 0 | 0 | — |
| 双网卡带宽 | 5162 MB/s | 4985 MB/s | −3% |

**要点**：
- **丢包大幅下降 79%** —— CC 最显著的效果。CC 通过感知拥塞主动降速，避免了缓冲溢出丢包。
- **重传下降 32%** —— 丢包少了，重传自然少。
- ECN 仍为 0 —— CORNV2 可能不依赖 ECN 标记（用其他拥塞信号如 RTT/CWND），或当前拥塞未触发 ECN 阈值。

---

## 3. 推理性能对比（c16, 1024/256, 48 请求）

| 指标 | CC=OFF | CC=ON(1) | CC=ON(2) | 变化 |
|------|---:|---:|---:|---:|
| 吞吐 tok/s | 402.7 | 393.9 | 393.5 | **−2.5%** |
| Mean TTFT ms | 6418 | 6690 | 6862 | +5-7% |
| P99 TTFT ms | 8585 | 9659 | 9888 | **+13-15%** |
| Mean TPOT ms | 8.88 | 9.05 | 9.10 | +2% |
| 失败 | 0 | 0 | 0 | — |

**要点**：
- CC=ON 两次复测一致 → **性能下降是真实的，不是噪声**。
- 吞吐降 2.5%、TPOT 升 2%（轻微，接近噪声阈值）。
- **P99 TTFT 升 13-15%** —— 最明显的代价。CC 的主动限速在高并发排队时增加了尾延迟。

---

## 4. 分析：为什么会这样

CC（拥塞控制）的工作原理是**发送端根据网络拥塞信号主动降低发送速率**，防止把交换机缓冲打满导致丢包。

- **好处**：丢包/重传大减（−79%/−32%）。丢包重传的代价是"发出去的数据白费 + 重发"，减少它理论上更高效、更稳定。
- **代价**：主动降速意味着峰值吞吐略降，且限速逻辑在高并发排队时放大了尾延迟（P99 +13%）。

**当前场景的特殊性**：之前 RDMA 全面分析已证明这套 200G 网络**利用率极低（<13%），是 compute-bound**。也就是说：
- 网络本来就不拥塞（丢包占比 <0.01%），CC 解决的"丢包"问题本身影响很小。
- 而 CC 的限速代价（吞吐/延迟）却实打实发生了。
- **所以在这个 compute-bound 场景，CC 打开是"治了个小病、付了点代价"。**

---

## 5. 建议

| 场景 | 建议 |
|------|------|
| **当前 TP=4 推理（compute-bound，网络空闲）** | **可关闭 CC**（disable_cc=Y）：丢包本就极少，关 CC 换取略高吞吐和更低 P99 延迟 |
| 网络成为瓶颈（更大模型/更高并发/更多节点） | **打开 CC**：当网络真正拥塞时，CC 避免丢包风暴的价值 > 限速代价 |
| 生产稳定性优先，能接受 2-3% 吞吐损失 | **打开 CC**：−79% 丢包带来更稳定可预测的网络行为 |
| 追求极限吞吐/最低延迟 | **关闭 CC** |

**针对你当前的 Qwen3.8-27B TP=4 场景**：网络远未饱和，CC 的收益（减少本就很少的丢包）小于代价（吞吐 −2.5%、P99 +13%）。**除非有稳定性硬需求，否则关闭 CC 对当前负载更优。**

但如果未来扩展规模（更多节点做 TP、或更大模型让通信量激增到接近饱和），CC 的价值会显现——建议届时重测。

## 6. 操作记录（可复现/回滚）

### 打开 CC
```bash
# 1. 停服务释放 RDMA（4节点容器）
./scripts/vllm_cluster_service.sh stop
for ip in <NODE0_IP>..<NODE3_IP>; do ssh $ip docker stop vllm-ray-node; done
# 2. 确认 arnic 引用计数=0（可卸载）
lsmod | grep '^arnic'
# 3. 重载驱动（每节点，需sudo）
sudo modprobe -r nvidia_peermem; sudo modprobe -r arnic
sudo modprobe arnic disable_cc=0; sudo modprobe nvidia_peermem
# 4. 配置交换机 CC（用户侧完成）
# 5. 重启：docker start → Ray 自动组网 → vllm_cluster_service.sh start
```

### 回滚（关闭 CC）
同上，把 `disable_cc=0` 改为 `disable_cc=1`。脚本：`scripts/arnic_reload_cc.sh disable`

### 验证 CC 状态
```bash
cat /sys/module/arnic/parameters/disable_cc   # N=开 Y=关
cat /sys/class/infiniband/arnic_0/cc_state    # 1=激活 0=未激活
```
