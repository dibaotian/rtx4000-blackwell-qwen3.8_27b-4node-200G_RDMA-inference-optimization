# CC (CORNV2) ON vs OFF 详细对比分析报告

> 日期：2026-08-30 | 配置：NVFP4 + TP=4 + DFlash n=7 | 算法：CORNV2（delay/RTT-based）
> 方法：用 `cornv2_cc_ctl.sh` 切换 CC，每状态重启 vLLM，跑 c1/c4/c16 三档负载
> 负载：random 1024 输入 / 256 输出，temp=0，相同 seed 逻辑
> 前提：**交换机 ECN 关闭**，CORNV2 靠 RTT/delay 信号工作（ECN 响应全程=0）

---

## 0. 核心结论（比单档测试更细致）

**CC 的效果随并发档位变化，不是单一方向：**

| 并发 | CC 对性能 | CC 对网络质量 | 判断 |
|------|-----------|--------------|------|
| **c1（低）** | ❌ 明显变差（P99 +49%） | ❌ drop 反而更多（245 vs 37） | CC 帮倒忙 |
| **c4（中）** | ➖ 基本持平（±2%） | ➖ 互有高低 | 无明显差异 |
| **c16（高）** | ✅ 反而更好（吞吐 +3.1%，P99 −3.6%） | ✅ drop 更少（507 vs 671） | CC 开始体现价值 |

**关键洞察：CC 在高并发（真正接近拥塞）时才有正收益；低并发时纯是代价。** 这修正了"CC 一律有代价"的粗略结论。

## 1. 性能对比（相同负载）

| 指标 | CC=ON | CC=OFF | ON vs OFF |
|------|---:|---:|---:|
| **c1 吞吐** | 131.4 | 134.6 | −2.4% |
| c1 Mean TTFT | 207 ms | 186 ms | +11.3% |
| **c1 P99 TTFT** | 295 ms | 198 ms | **+49%** ❌ |
| c1 TPOT | 6.83 ms | 6.73 ms | +1.5% |
| c4 吞吐 | 354.2 | 356.7 | −0.7% |
| c4 P99 TTFT | 693 ms | 700 ms | −1.0% |
| c4 TPOT | 9.68 ms | 9.49 ms | +2.0% |
| **c16 吞吐** | 409.6 | 397.2 | **+3.1%** ✅ |
| c16 Mean TTFT | 6482 ms | 6613 ms | −2.0% |
| **c16 P99 TTFT** | 9614 ms | 9977 ms | **−3.6%** ✅ |
| c16 TPOT | 8.72 ms | 9.10 ms | −4.2% ✅ |

**读法**：吞吐越高越好，延迟越低越好。
- **c1**：CC=ON 全面变差，尤其 P99 +49%（低并发下 CC 的窗口探测纯属多余开销）。
- **c4**：差异都在 ±2%，属噪声范围。
- **c16**：CC=ON 全面反超（吞吐、TTFT、TPOT、P99 都更好）——高并发下 CC 的限速避免了拥塞崩溃。

## 2. 网络质量对比（retx 重传 / drop 丢包）

| 指标 | CC=ON | CC=OFF |
|------|---:|---:|
| c1 retx | 2 | 0 |
| c1 drop | 245 | 37 |
| c4 retx | 36 | 139 |
| c4 drop | 181 | 40 |
| c16 retx | 285 | 331 |
| **c16 drop** | **507** | **671** |

- **c1**：CC=ON 丢包反而多（245 vs 37）—— 反常，见 §3 分析。
- **c4**：retx/drop 互有高低，无定论。
- **c16**：CC=ON 丢包更少（507 vs 671，−24%），重传也略少 —— 高并发下 CC 确实在减少拥塞丢包。

**ECN 响应两组全程 = 0**：证实 CORNV2 是 delay-based，不依赖交换机 ECN（ECN 已关闭）。

---

## 3. 为什么低并发 CC 反而更差？（关键分析）

这是本次最反直觉的发现：**c1 低并发时 CC=ON 的丢包（245）比 CC=OFF（37）还多，P99 延迟高 49%。**

原因推断：

**① 低并发本无拥塞，CC 的窗口探测是纯开销**
- c1 时网络极空闲，根本不会拥塞丢包。
- CORNV2 仍执行窗口（cwin）探测/调整逻辑（从 init_cwin=1520 爬坡），这个"试探性发送 + 窗口调整"在无拥塞时纯属多余，反而增加了首包延迟（P99 +49%）。

**② CC=ON 的 drop 更多可能是测量/机制假象**
- 245 vs 37 的绝对量都极小（占总包数 <0.01%），可能是 CORNV2 窗口调整时的瞬时行为差异，或采样窗口噪声。
- 低并发下这点 drop 对端到端性能影响微乎其微，但 P99 +49% 是真实的（窗口探测开销）。

**③ 高并发才是 CC 的主场**
- c16 时 16 条流竞争，真的开始拥塞（CC=OFF drop 达 671）。
- 此时 CORNV2 的限速正好避免了缓冲溢出，drop 降到 507，且因为避免了拥塞崩溃，吞吐/延迟反而更好。

**一句话**：CC 是"拥塞保险"——低并发（无险）时白交保费（P99 代价），高并发（有险）时才理赔（性能反超）。

## 4. 与上次单档测试的差异说明

上次（`congestion-control-test.md`）只测 c16，得出"CC 吞吐 −2.5%、P99 +15%"。本次多档测试发现：
- **上次 c16 的负向结果未复现**——本次 c16 CC=ON 反而更好（吞吐 +3.1%）。
- 差异原因：投机解码/负载有随机性，单次 c16 采样波动大；**多档 + 本次数据更可信**。
- 结论修正：CC 的效果**强依赖并发档位**，不能用单档下定论。

## 5. 最终建议（基于多档数据）

| 你的实际并发场景 | 建议 |
|------|------|
| **主要是低并发（1-4 个 agent，当前 Codex 场景）** | **关闭 CC**：低并发 CC 纯代价（P99 +49% @c1），无收益 |
| 主要是高并发（16+ 持续压力） | **打开 CC**：高并发下 CC 反而提升吞吐/降低尾延迟 |
| 混合/不确定 | 看主力负载；若以低并发交互为主，倾向关闭 |

**针对你当前对接 Codex 的场景（少量并发 1-4）**：**关闭 CC 更优**——低并发下 CC 的 P99 代价明显，而收益（减少本就极少的丢包）可忽略。

**但如果未来上高并发生产（大量并发请求）**：应打开 CC，它在 c16 已显示正收益，规模更大时价值更明显。
