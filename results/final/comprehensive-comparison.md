## 1. 单卡为什么全是 ❌（结构性，不是没测）

| 尝试 | 结果 | 原因 |
|------|------|------|
| 单卡 FP8 | ❌ 无法运行 | FP8 权重 28.75GiB > 单卡 24GB 显存，物理放不下 |
| 单卡 BF16 | ❌ 无法运行 | BF16 约 54GiB，更放不下；且磁盘无 BF16 权重 |
| 单卡 NVFP4 | ⚠️ 权重可放但 KV 紧张 | NVFP4 权重 22.3GB，单卡放下后 KV 仅剩 ~1GiB，长 context 受限。已下载 unsloth NVFP4，本次用 TP=4 测（见 §2a） |

**结论**：27B 模型在 24GB 单卡上，只有 NVFP4/W4A16 这类 4-bit 量化才可能塞下。**已下载 unsloth NVFP4（22.3GB）**，但单卡放下权重后 KV 空间不足，实用性差；本次用 **NVFP4 + TP=4**（每卡仅 ~5.5GiB，KV 充裕）测试，见 §2a。真正的「单卡 DP=4」需更小的 NVFP4（如 QUASAR 20.6GB）且接受短 context。

## 2a. NVFP4 量化实测（unsloth，TP=4）⭐ 新增

下载 `unsloth/Qwen3.8-27B-NVFP4`（22.3GB，compressed-tensors 格式，保留 MTP），TP=4 加载成功，Blackwell FP4 内核 `FlashInferCutlassNvFp4LinearKernel` 启用。

### 速度对比（ShareGPT 真实数据，temp=0）
| 配置 | 单请求 | 并发4 | 单请求TPOT |
|------|---:|---:|---:|
| FP8 无投机 | 42.8 | — | 23.2ms |
| **NVFP4 无投机** | **48.4** | — | 20.0ms |
| NVFP4 + MTP n=3 | 97.4 | 301.3 | 9.9ms |
| **NVFP4 + DFlash n=7** | 86.6 | **311.0** | 11.1ms |

- **NVFP4 纯量化比 FP8 快 +13%**（48.4 vs 42.8）——Blackwell FP4 算力 + 权重更小。
- NVFP4 上 **MTP（97.4）单请求略优于 DFlash（86.6）**，与 FP8 上相反（可能因 unsloth 的 MTP 层随权重一起 NVFP4 优化）。
- NVFP4 + DFlash 并发4 = **311 tok/s**，全项目最高聚合吞吐。

### 显存/KV 优势
| | FP8 | NVFP4 |
|---|---:|---:|
| 权重/卡（TP=4） | 7.1GiB | ~5.5GiB |
| **KV cache 容量** | 1.45M tokens | **1.82M tokens（+26%）** |

NVFP4 权重更小，KV 空间多 26%，长 context 并发更宽裕。

### ⭐ 质量对比（你最担心的能力下降）——实测无实质下降

**15 题扩展测试（算术/代数/常识/代码/逻辑，temp=0）：FP8 = 15/15 全对，NVFP4 = 15/15 全对。**

| 类别 | 题目 | FP8 | NVFP4 |
|------|------|:---:|:---:|
| 大数乘法 | 234×567=132678 | ✅ | ✅ |
| 代数 | x+15=3x → 7.5 | ✅ | ✅ |
| 幂 | 2^10=1024 | ✅ | ✅ |
| 斐波那契 | 第10个=55 | ✅ | ✅ |
| 一年秒数 | 31536000 | ✅ | ✅ |
| 常识/代码/逻辑 | 北京/H₂O/DNA/递归/质数等 | ✅ | ✅ |

- 另一组 5 题（更难算术）中两者各错 1 道（FP8 错 127×43+891，NVFP4 错「100天后星期几」）——**都是量化通病的算术小误差，非 NVFP4 独有**，且 FP8 也会错。
- **结论：unsloth NVFP4 的能力与 FP8 实测无实质差异**。unsloth 官方称保留 92-97% 准确率，本测试未观察到有意义的退化。生产切换前若有特定关键任务，建议用你的真实评测集再确认。

**注**：本测试为快速验证，样本有限。严格的能力评估需跑标准 benchmark（MMLU/GSM8K/HumanEval 等），但当前结果足以说明「不会大幅掉能力」。

## 2b. temperature=0（贪心解码）加速详解

单路 profiling 发现的最大优化点。单请求 78→**96.5 tok/s（+24%）**，并发4 242→**313（+29%）**。

### 什么是 temperature（温度）？

Temperature 是大模型**采样阶段**的一个参数，控制"下一个 token 如何从概率分布里挑选"：

- 模型每一步会对词表里所有 token 输出一个概率分布（比如 "今天天气很" 之后："好"=70%、"热"=15%、"冷"=8%…）。
- **temperature 控制这个分布的"陡峭 / 平缓"程度**：
  - `temperature = 0`：**贪心解码（greedy）**——永远选概率最高的那个 token（"好"）。输出**完全确定**，同样输入每次输出一模一样。
  - `temperature = 1`：按原始概率分布随机采样，保留模型原本的随机性。
  - `temperature > 1`（如 1.5）：分布被"压平"，低概率 token 更容易被选中，输出更**发散、有创意、也更容易跑偏**。
  - `0 < temperature < 1`（如 0.7）：介于两者之间，有一定随机性但偏向高概率 token（多数对话应用的默认值）。

### 为什么 temp=0 会让投机解码更快？

投机解码（DFlash/MTP）的原理：**草稿模型先猜若干 token，主模型一次性验证，猜中的就"免费"产出**。加速幅度 = 接受率。

- **temp=0（贪心）**：主模型的输出是**确定的最高概率 token**，草稿模型也是朝"最可能"方向猜——两者目标一致，**草稿命中率高**。实测接受率 27%→**35%**。
- **temp>0（随机采样）**：主模型会按概率随机选，有时选中非最高概率 token，草稿就猜不中——**接受率低，加速小**。

所以 temp=0 不是"调快了模型"，而是"让草稿更容易猜中"，间接提升了投机的效率。

### ⚠️ 关键：这不是"免费"加速，是质量/速度权衡

temp=0 会**改变输出内容**——从"有随机性的采样"变成"确定性的贪心"。这不是 bug，但要按场景选：

| 场景 | 是否推荐 temp=0 | 原因 |
|------|:---:|------|
| **代码生成** | ✅ 强烈推荐 | 代码要正确、可复现，贪心正好是首选，还白赚 +24% 速度 |
| **数学 / 逻辑推理** | ✅ 推荐 | 追求唯一正确答案，确定性有利 |
| **信息抽取 / 分类 / 结构化输出（JSON）** | ✅ 推荐 | 要求稳定、可复现，不需要多样性 |
| **翻译 / 摘要** | ✅ 大多推荐 | 通常要忠实、稳定，贪心可接受 |
| **RAG 问答 / 事实问答** | ✅ 推荐 | 要准确不要发散 |
| **创意写作 / 故事 / 头脑风暴** | ❌ 不推荐 | 需要多样性和创造力，贪心会单调、重复 |
| **多样化对话 / 角色扮演** | ❌ 不推荐 | 每次回复都一样会很生硬 |
| **需要多次采样取最优（best-of-n）** | ❌ 不适用 | 贪心每次输出相同，无法采多个候选 |

### 重要澄清：投机解码本身对任何 temperature 都"无损"

- 投机解码在**任何 temperature 下都不改变输出分布**（vLLM 的实现是数学无损的）——temp=0.7 开投机，输出和 temp=0.7 不开投机在统计上一致，只是速度不同。
- **temp=0 的 +24% 是"额外红利"**：因为贪心让草稿更易命中，加速更大。但代价是你选择了贪心这种采样策略本身（牺牲多样性）。
- 换句话说：**如果你的业务本来就该用 temp=0（代码/抽取等），那这 +24% 是纯赚的**；如果业务需要多样性（temp>0），投机解码仍有效，只是加速幅度小一些（用真实数据 §0c 的默认采样那几行）。

### 生产使用方法

不需要改服务配置，**由每个 API 请求自己指定**：
```json
{"model": "qwen3.8-27b", "prompt": "...", "temperature": 0}
```
可以按请求类型动态设置：代码/抽取类请求发 `temperature: 0`（享受 +24% 加速），创意类请求发 `temperature: 0.7`（保多样性）。同一个服务同时支持。

## 3. TP vs PP：核心对比（这是最有价值的发现）

### 同卡数下 TP 完胜 PP（单请求）
| 卡数 | PP 单请求 | TP 单请求 | TP 优势 |
|---:|---:|---:|---:|
| 2 | 20.0 tok/s（PP=2） | 33.9 tok/s（TP=2） | **+70%** |
| 4 | 20.6 tok/s（PP=4） | 42.2 tok/s（TP=4） | **+105%** |

### 关键洞见：PP 卡数增加，单请求几乎不提升
| 配置 | 单请求 tok/s | TPOT |
|------|---:|---:|
| PP=2 | 20.0 | 47.9ms |
| PP=4 | 20.6 | 23.4ms* |

PP=2 和 PP=4 单请求吞吐**几乎一样**（20.0 vs 20.6）。因为 PP 是**串行流水线**——一个请求必须依次穿过所有 stage，加卡只是增加流水线段数，不加速单个 token。（*PP=4 的 TPOT 23ms 看似更低，是因 CUDA graph 与调度差异，但吞吐仍未提升，说明流水线气泡是瓶颈。）

### TP 卡数增加，单请求线性提升
| 配置 | 单请求 tok/s | TPOT | 相对单位 |
|------|---:|---:|---:|
| TP=2 | 33.9 | 29.1ms | 基准 |
| TP=4 | 42.2 | 23.4ms | +24% |

TP 加卡真正加速单请求——4 卡并行算同一层，TPOT 从 29ms 降到 23ms。虽非完美线性（受跨节点 all-reduce 开销），但方向正确。

**结论**：在"低延迟 + 单请求/小并发"场景（正是本项目 goal 的重点），**TP 全面优于 PP**。PP 唯一的场景优势是超长 context（每卡放更多层但 KV 需求分摊方式不同）——但实测 PP=2 反而因每卡放 32 层挤占 KV，装不下 262K（见 §5）。

**定性结论（不受数据类型影响）**：投机解码在 2 卡和 4 卡 TP 上**都有效**，MTP 只能在 TP 下开（PP 不支持 `Qwen3_5MTP`）——这是选 TP 的又一理由。

|------|---:|---:|---:|

| DFlash n=6 | 73.2 | **251.9** | 并发4 最优 |

（早期随机数据曾报 MTP 单请求 102，已失真删除，勿引用；真实数据见 §0c。）

## 5. 一个副产品结论：PP=2 装不下 262K context

实测 PP=2 启动时报错：
> `ValueError: 4.16 GiB KV cache needed > 4.02 GiB available. Estimated max model length is 252448.`

**原因**：PP=2 把 64 层切成 2 段，每卡放 32 层权重（PP=4 每卡只放 16 层）。权重占用翻倍，留给 KV 的显存变少，262K 的 KV（4.16GiB）放不下。所以 PP=2 测试用了 `max_model_len=131072`。

**含义**：更少的卡做 PP，不仅不提速，还牺牲最大 context。这进一步说明 PP 在本硬件上不是好选择。（TP 因每卡只放 1/4 层权重，KV 空间最充裕——TP=4 的 KV 达 1.5M tokens，全场最大。）

## 8. 优化历程（全部实测、单变量、可复现）

```
单卡              ❌ 放不下（FP8 28.75GiB > 24GB）
  ↓ 必须多卡
PP=4（原始生产）   20.6 tok/s   ← 旧文档的配置
  ↓ 换 TP（推翻"TP跑不起来"）
TP=4              42.6 tok/s   (2.1×)
  ↓ 加投机（推翻"MTP不可用"）+ 真实数据
TP=4 + DFlash n=7 78.2 tok/s   (3.7×)  ← 当前生产（真实数据单请求）
```

**从 20.6 到 78.2 tok/s（真实数据单请求），累计 3.7 倍**；并发4 达 252 tok/s。两个关键突破来自实测推翻旧文档的"不可能"结论（TP 跑不起来、MTP 不可用），第三个来自用真实数据纠正随机数据的失真。

> 注：随机数据曾报单请求 126 tok/s（DFlash）/102（MTP），但随机 token 失真，真实数据（ShareGPT）单请求更低、并发更高。生产参考以真实数据为准。
