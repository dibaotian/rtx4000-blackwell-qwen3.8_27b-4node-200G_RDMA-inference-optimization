# RDMA 全面分析报告（TP=4 生产负载实测）

> 日期：2026-08-30 | 配置：NVFP4 + TP=4 + DFlash n=7 | 双 200G ARNIC RoCE v2
> 方法：ARNIC hw_counters 在多种真实负载下采样，4 节点 × 双网卡全维度
> 数据来源：`/sys/class/infiniband/arnic_{0,1}/ports/1/hw_counters/`

---

## 0. 一句话结论

**RDMA 绝非瓶颈**：即使峰值负载，单网卡利用率也 <13%（每节点还有双网卡 = 2×200G）；网络质量健康（重传/丢包 <0.01%，零拥塞、零内存错误）；延迟稳定在 3.9-7μs。**瓶颈明确在 GPU 算力（compute-bound）。**

---

## 1. 带宽利用率：四种负载状态

| 状态 | 每网卡带宽 | 单网卡利用率 | 双网卡合计 | GPU util |
|------|---:|---:|---:|---:|
| 空闲 | 0 | 0% | 0 | — |
| 单请求（并发1）| ~419 MB/s | 1.7% | 838 MB/s | 89-97% |
| 并发4 decode | ~1770 MB/s | **7.1%** | 3126 MB/s | 79-98% |
| Prefill 活跃峰值 | ~3071 MB/s | **12.3%** | 6142 MB/s | 99% |

**要点**：
- 利用率口径 = 单张网卡带宽 / 200 Gbit/s（每卡对比自己的链路）。
- **最高负载（prefill 峰值）单网卡也才 12.3%**，每节点双网卡（400G）则 <7%。
- RDMA 有 **87% 以上余量**，加快网络对性能无帮助。

---

## 2. 全集群 per-node 视角（并发4 decode，4节点×双网卡）

| 节点 | arnic_0 TX | arnic_1 TX | retx | drop | RTT max |
|------|---:|---:|---:|---:|---:|
| node0 | 1734 MB/s | 1730 MB/s | 76 | 0 | 6.8μs |
| node1 | 1753 | 1750 | 0 | 30 | 4.7μs |
| node2 | 1774 | 1771 | 0 | 76 | 5.5μs |
| node3 | 1793 | 1790 | 30 | 0 | 4.7μs |

**全集群合计：14,096 MB/s = 112.8 Gbps**（每节点 ~3524 MB/s）

**要点**：
- **4 节点流量高度均衡**（1734-1793 MB/s），TP all-reduce 对称，无热点节点。
- **双网卡完美均衡**（arnic_0 ≈ arnic_1），NCCL `NCCL_IB_HCA=arnic_0,arnic_1` 双 HCA 负载分摊工作正常，两条 200G 都用上。
- retx/drop 分散在不同节点/网卡，无单点集中（非硬件故障特征）。

## 3. 网络质量（26 个计数器全检）

| 指标 | 计数器 | 实测 | 判定 |
|------|--------|------|------|
| 重传 | `cs_retx_wr` | 单请求 0；并发4 ~40/节点/20s；60s 累计 +135 | ✅ <0.01% 包，缓慢非线性 |
| 丢包 | `rx_drop` | 0-40/节点/20s | ✅ 极低 |
| 拥塞标记 | `cs_rx_ecn_resp` | **全程 0** | ✅ 无拥塞 |
| 内存错误 | `local/remote_mr_errors` | **0** | ✅ 无 RDMA 故障 |
| FCS 错误 | `rx_fcs_errors` | 0 | ✅ 物理层健康 |
| 完成丢弃 | `rx_cmpl_drop` | 0 | ✅ |
| 接收队列空丢弃 | `rx_rq_empty_drop_cnt` | 0 | ✅ 无缓冲不足 |
| 重复接收 | `cs_dup_rx_wr` | 0 | ✅ |
| NACK 裁剪 | `cs_rx_trimmed_nack` | 0 | ✅ |

**要点**：
- 唯一非零的是 retx/drop，但**占总包数 <0.01%**，且长期观察增长缓慢非线性（非持续劣化）。
- **零 ECN、零 MR 错误、零 FCS 错误** = 网络物理层和拥塞控制都健康。
- ⚠️ 高并发下 retx 从 0 开始出现，**建议纳入长期监控**看是否随负载规模恶化。

## 4. 延迟分析（TP 通信的关键指标）

| 指标 | 计数器 | 实测值 |
|------|--------|--------|
| 新请求 RTT 最小 | `cs_new_wr_rtt_min` | 3868 ns（3.9μs） |
| 新请求 RTT 最大 | `cs_new_wr_rtt_max` | 4032-6968 ns（4.0-7.0μs） |
| 重传 RTT | `cs_ret_wr_rtt` | 0（无重传路径延迟） |

**要点**：
- **TP=4 的 all-reduce 是小消息高频通信，延迟比带宽更关键**。
- RTT 稳定在 **3.9-7μs**（RoCE v2 正常范围），无突增到几十/上百μs → 无排队/拥塞。
- 这个延迟水平对 TP 每 token 每层同步是足够低的，不构成瓶颈。

---

## 5. 通信模式（TP all-reduce 特征）

| 指标 | 实测 | 含义 |
|------|------|------|
| 平均包大小 | 2016 bytes（MTU 4096 的 49%） | 包未填满，小消息为主 |
| 包速率 | 278-776 Kpps | 高频 |
| goodput/tx 比 | ≈ 100% | RoCE 协议开销极低，有效吞吐≈原始 |
| 通信增长 | 单请求→并发4 约 3.7× | 与 decode 吞吐正相关 |

**要点**：
- 平均包 2016B + 高频 = **典型 TP all-reduce 小消息模式**。
- 通信量随 decode 吞吐线性增长（每 token 每层 all-reduce），符合 TP 理论。
- Prefill 峰值带宽更高（6142 MB/s）但持续短；decode 是持续的中等带宽。

---

## 6. 瓶颈判定（决策树）

```
实测：GPU util 79-99% + 单网卡 RDMA 利用率 <13% + retx/drop<0.01% + ECN=0
                              ↓
                    compute-bound（算力瓶颈）
```

| 判据 | 阈值 | 实测 | 结论 |
|------|------|------|------|
| GPU 利用率 | >90% 为高 | 79-99% | ✅ 高 |
| RDMA 单网卡利用率 | <30% 为低 | <13% | ✅ 低 |
| 网络质量 | retx/drop 稳定 | <0.01% | ✅ 健康 |
| 延迟 | RTT 稳定 | 3.9-7μs | ✅ 健康 |

**→ 教科书级 compute-bound：GPU 算力打满，RDMA 在等着喂数据。这套 200G RDMA（每节点双网卡 400G）对 TP=4 绰绰有余。**

---

## 7. 对优化的指导意义

1. **加快网络无用**：RDMA 有 87%+ 余量，换更快网卡/NVLink 不会提升当前 TP=4 性能（瓶颈在 GPU）。
2. **想提性能只能从 GPU 侧**：更强算力 GPU、更激进量化（已用 NVFP4）、投机解码（已用）。
3. **200G RDMA 对这个规模是过剩配置**：如果只跑 Qwen3.8-27B TP=4，理论上 100G 甚至更低也够（但 RDMA 也用于 Ray/NCCL 控制面，且更大模型/更高并发会用更多）。
4. **值得长期监控 retx**：高并发下开始出现重传，虽当前可忽略，但应观察是否随生产负载规模恶化——这是唯一的潜在关注点。

---

## 8. 局限与注意

- **采样窗口影响读数**：prefill 短（<2s）难精确对齐，本报告 prefill 数据为活跃期瞬时峰值，非平均。
- **计数器为节点级共享**：含 Ray/NCCL 控制面流量（实测空闲时为 0，故推理占主导）。
- **利用率口径**：本报告统一用「单网卡 / 200G」；若按「双网卡 / 400G」利用率减半。
- ARNIC 为定制 provider，标准 `port_xmit_data` 不可用，本报告基于其专有 `cs_*` 计数器。
