# 为什么打开拥塞控制（CC）会有性能代价 — 机理分析

> 日期：2026-08-30 | 算法：CORNV2（ARNIC 基于窗口的拥塞控制）
> 配套数据见 `congestion-control-test.md`；本文只讲**代价的成因机理**

---

## 0. 问题

实测打开 CC 后：
- ✅ 丢包 −79%、重传 −32%（网络质量改善）
- ❌ 吞吐 −2.5%、P99 TTFT +13%、TPOT +2%（性能代价）

**为什么改善网络质量要付出性能代价？代价具体从哪来？** 本文逐层拆解。

---

## 1. 先理解 CC 在做什么：从"敢发就发"到"看路况发"

### CC=OFF（关闭拥塞控制）
发送端**不管网络状况，有数据就全速发**。
- 好处：没有任何限速逻辑，峰值吞吐最高、延迟最低。
- 坏处：多个发送端同时猛发时，交换机缓冲被打满 → **丢包** → 丢的包要**重传** → 浪费带宽 + 增加延迟抖动。

### CC=ON（打开拥塞控制，CORNV2）
发送端**根据网络拥塞信号动态调整发送窗口（cwin）**，主动限速避免打满缓冲。
- 实测 CORNV2 参数：`init_cwin=1520`（初始窗口）、`min_cwin=16`（拥塞时最小窗口）。
- 好处：主动避让 → 缓冲不溢出 → **丢包大减**。
- 坏处：限速本身 = 牺牲一部分发送速度 → **代价的根源**。

---

## 2. 代价来源逐项拆解

### 代价一：吞吐 −2.5% —— 限速的直接结果

CORNV2 是**基于窗口（cwin）**的算法。发送端任一时刻"在途未确认数据量"受 cwin 限制：

```
CC=OFF: cwin 无限制 → 一次可压满链路 → 峰值带宽
CC=ON:  cwin 受控（16~1520）→ 探测到拥塞就缩窗 → 发送速率被"削峰"
```

- 当 CC 感知到轻微拥塞信号（如 RTT 上升），就**主动缩小 cwin**，降低发送速率。
- 这个"削峰"直接反映为**峰值吞吐下降 2.5%**。
- 本质：CC 用"少发一点"换"不丢包"，吞吐是付出的第一笔代价。

### 代价二：P99 TTFT +13% —— 窗口探测的尾延迟放大

这是最明显的代价（+13-15%），成因有二：

**① 慢启动 / 窗口探测的爬坡开销**
- CC 从 `init_cwin=1520` 开始，需要**逐步探测**能安全发多快（窗口逐渐增大）。
- 一个新请求的首包（prefill 后第一批数据）要经历这个"试探性发送"阶段，比 CC=OFF 的"直接全速"慢。
- 反映为 **TTFT（首 token 延迟）上升**。

**② 高并发排队时的限速叠加**
- c16 时 16 个请求的通信同时竞争，CC 对每条流都限速。
- 限速在**尾部请求**（排队最久的）上累积效应最强 → **P99（99分位）延迟被放大**，比平均 TTFT（+5%）涨得更多（+13%）。
- 即：CC 让"最慢的那批请求"更慢，因为它们既排队又被限速。

### 代价三：TPOT +2% —— decode 每步的轻微限速

- decode 每 token 每层要 all-reduce，CC 对每次 all-reduce 通信都施加窗口控制。
- 每步增加极小的限速开销，累积成 TPOT +2%（接近噪声，但方向一致）。

---

## 3. 为什么在"这个场景"代价尤其不划算

关键：**CC 的收益取决于网络本来有多拥塞。而这套网络本来就不拥塞。**

前置事实（见 `rdma-full-analysis.md`）：
- 200G 链路利用率 **<13%**（峰值），是 **compute-bound**（GPU 打满、网络空闲）。
- CC=OFF 时丢包率 **<0.01%**（705 个丢包 / 数千万包）。

所以在当前场景：

| | CC 解决的问题 | CC 付出的代价 |
|---|---|---|
| 规模 | 丢包本就 <0.01%（极小） | 吞吐 −2.5%、P99 +13%（实打实） |
| 类比 | 治一个几乎没有的"小病" | 却吃了有副作用的药 |

**核心矛盾**：CC 是为"网络真拥塞"设计的。当网络空闲（利用率 <13%），拥塞几乎不存在，CC 的限速逻辑**只带来代价、收不到对应的好处**。丢包从 705→150 看似改善大，但 705 本身占比就微不足道，对端到端性能几乎无影响；而限速的 2.5%/13% 却真实作用在每个请求上。

---

## 4. 那 −79% 丢包为什么没转化成性能提升？

直觉上"少丢包 = 少重传 = 更快"，为什么这里反而更慢？

因为**重传的绝对量太小，省下来的不够补限速的亏**：
- CC=OFF：705 丢包 → 481 重传。重传浪费的带宽 = 481 个 work request，相对 5162 MB/s 的总流量**微不足道**（<0.1%）。
- CC=ON：省下 555 个丢包 + 155 个重传，但为此对**所有**流量限速（−2.5% 吞吐作用在 100% 流量上）。

**省的是 0.1% 的重传浪费，付的是 2.5% 的全局限速** → 净亏。

只有当丢包/重传规模大到（比如网络饱和时丢包率 5-10%），重传浪费本身成为主要开销时，CC 消除它的收益才会 > 限速代价。

---

## 5. 一张图总结代价链条

```
打开 CC (CORNV2 窗口控制)
      │
      ├─→ 窗口限速(cwin) ──→ 峰值发送速率下降 ──→ 吞吐 −2.5%
      │
      ├─→ 窗口爬坡探测 ────→ 首包试探性发送 ──→ TTFT ↑
      │        └─→ 高并发下尾部请求限速叠加 ──→ P99 TTFT +13%
      │
      └─→ 每步 all-reduce 限速 ──→ TPOT +2%

  收益: 丢包 −79% / 重传 −32%
  但: 网络本就 <13% 利用率、丢包 <0.01%
      → 收益规模 << 代价规模 → 当前场景净亏
```

---

## 6. 结论

1. **代价的根源是"限速"**：CC 通过窗口控制主动降低发送速率来避免丢包，限速直接换来吞吐下降、延迟上升。
2. **P99 延迟涨最多（+13%）**：因为窗口爬坡 + 高并发尾部限速叠加，最慢的请求被放大。
3. **当前场景不划算**：网络 compute-bound、利用率 <13%、丢包 <0.01%，CC 解决的问题规模远小于它的限速代价。
4. **CC 不是"坏"，是"用错场景"**：它为拥塞网络设计。当前网络不拥塞，所以只见代价不见收益。**扩大规模（更多节点/更大模型/通信接近饱和）后，CC 才会体现价值——届时应重测。**
